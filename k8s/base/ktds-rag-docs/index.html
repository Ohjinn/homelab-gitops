1. 이게 뭔가#

우리 팀 Azure 표준대로 테라폼을 쓰게 돕는 RAG 시스템이다.

목표가 "코드를 잘 쓰는 것" 이 아니라는 점이 중요하다. 진짜 목표는 아는 것과 모르는 것을 구분시키는 것이다.

LLM 은 일반적인 Azure 를 안다. Terraform 문법도 알고 azurerm_application_gateway 도 안다. 인터넷 문서가 학습에 다 들어갔기 때문이다. 그런데 우리 표준은 모른다. 사내 레포라 학습 데이터에 없다. 그래서 그냥 물어보면 "일반적으로 이렇게 합니다" 를 답하는데, 문제는 그게 우리 표준이 아니라는 걸 사용자가 알 방법이 없다는 것이다. 그럴듯하기 때문이다.

이 시스템은 답할 때마다 근거가 어디서 왔는지 대괄호로 표시한다. 5 절에서 자세히 설명한다.

원본과의 관계#

농협몰 프로젝트에서 쓰던 Azure CLI 생성기의 문서에서 표준 부분만 떼어 테라폼 생성기로 만드는 것이다. 그래서 레퍼런스 안에 남아 있는 CLI 산출물 규정 (*-azure-cli-generation.md)은 코퍼스에서 제외했다. 검색되면 모델이 az 명령을 뱉는다. 그 자리를 azure-terraform-standard(테라폼 표준 모듈)가 대신한다.

2. RAG 가 뭔가#

이 절은 RAG 를 처음 보는 사람을 위한 것이다. 아는 사람은 3 절로.

왜 파인튜닝이 아니라 RAG 인가#

모델에게 우리 표준을 가르치는 방법이 둘이다.

파인튜닝 RAG
방식 모델을 우리 문서로 추가 학습 질문할 때마다 관련 문서를 찾아 프롬프트에 같이 넣음
비용 GPU 시간이 많이 듦 검색 비용만
문서 변경 다시 학습해야 함 인덱스만 다시 만들면 즉시 반영
출처 표시 불가능 — 가중치에 녹아듦 가능 — 어느 문서에서 왔는지 안다

시험에 비유하면 암기(파인튜닝) vs 오픈북(RAG) 이다. 오픈북은 교재가 개정되면 새 책만 가져가면 된다. 대신 문제집에서 맞는 페이지를 펴는 게 관건이 된다.

우리가 하는 일의 대부분이 그 "맞는 페이지 펴기" 다.

맞는 페이지를 어떻게 펴나 — 임베딩#

문제: 컴퓨터는 "비슷한 뜻" 을 모른다. 글자로 매칭하면 "App Gateway" 와 "애플리케이션 게이트웨이" 는 완전히 다른 문자열이다.

해법: 문장을 숫자 벡터로 바꾼다. 우리가 쓰는 bge-m3 모델은 문장 하나를 1024 개의 숫자로 바꾼다.

핵심은 이 변환이 아무렇게나 되는 게 아니라는 점이다. 뜻이 비슷한 문장은 숫자들도 비슷해지도록 훈련된 모델이다. 훈련 방식은 대조 학습(contrastive learning)인데, "이 둘은 같은 뜻 / 이 둘은 다른 뜻" 쌍을 수억 개 보여주면서 같은 뜻은 가깝게, 다른 뜻은 멀게 밀고 당긴다.

학부 ML 용어로는 문장을 1024 차원 공간의 한 점으로 사상(embedding) 하는 것이다. 그러면 "비슷한 뜻 찾기" 가 점 사이의 거리 재기가 된다. 두 점 사이 거리 공식을 1024 차원으로 확장한 것뿐이다.

bge-m3 를 고른 이유는 다국어 모델이기 때문이다. 우리 문서는 한국어 본문에 영어 기술 용어가 섞여 있는데 영어 중심 모델은 이걸 제대로 못 잡는다.

거리 숫자 읽는 법#

낮을수록 가깝다. 우리 설정은 L2 제곱 거리라 0~4 범위다. 코사인 유사도가 아니므로 "0.8 이면 80% 비슷" 같은 해석은 틀린다.

실측값 (2026-09-05):

질문 종류 최상위 거리
표준에 있는 질문 15 개 0.472 ~ 0.771
표준에 없는 질문 24 개 0.807 ~ 1.227

4. 파일별 역할#

① collect_docs.py — 수집과 선별#

존재 이유: RAG 에는 문서 단위 권한이 없다. 인덱스에 한 번 들어간 내용은 질의할 수 있는 누구에게나 보인다. "넣지 않는 것" 이 유일한 통제 수단이라 그 결정을 이 파일 한 곳에 모은다.

SOURCES 리스트가 이 파일의 전부다.

Source(
    alias="lz-reference",       # data/lz-reference/ 폴더명이자 검색 필터 값
    root=...,                   # 원본 경로
    exts={".md"},               # 이 확장자만 본다
    authority="parent",         # parent | child
    priority=100,               # 클수록 우선
    exclude={"00-index", "14-azure-cli-generation"},   # 아예 안 넣음
    pinned={"01-scope-and-reference-policy", ...},     # 검색 말고 항상 프롬프트에
    category="landing-zone",
)

exclude 와 pinned 는 다르다. exclude 는 넣지 않을 것, pinned 는 검색하지 말고 항상 넣을 것이다.

주요 함수:

함수 하는 일
wanted() 확장자로 1 차 필터
excluded() 경로 문자열로 2 차 필터. 비교 전에 \ → / 통일
categorize() pinned 면 control, 아니면 소스 지정값 또는 확장자 매핑
collect_git_log() 커밋 이력을 마크다운으로 뽑음
collect() 본체. 순회 → 필터 → 시크릿 검사 → data/ 복사 → manifest 기록

원본을 직접 인덱싱하지 않고 사본을 뜨는 이유가 둘이다. 무엇이 들어갔는지 data/ 를 열어보면 알 수 있고, 시크릿 필터를 한 곳에서 걸 수 있다.

커밋 이력을 뽑는 이유: 코드는 현재 상태만 보여주지만 커밋 메시지에는 "왜 그렇게 했는지" 와 "무엇을 하지 않기로 했는지" 가 남는다. 파일 어디에도 없는 정보다.

② build_index.py — 청킹과 임베딩#

함수 하는 일
breadcrumb() 청크 앞에 붙일 출처 경로 생성
table_headers_of() / header_for() / restore_table_header() 잘린 표 조각에 머리글 복원
split_markdown() 헤더 경계로 자른 뒤 1200 자 상한 적용
split_plain() 코드·인프라 파일용
chunk() 확장자별로 분할기를 골라 호출하고 메타데이터를 붙임
read_index() 기존 인덱스에서 해시를 읽어 증분 판단
build() 본체

breadcrumb 이 검색 품질에 제일 크게 작용한다.

azure-standard/modules/network/appgw/README.md > modules/network/appgw > 서브넷은 전용 /24 로 잡는다

이걸 청크 본문 맨 앞에 붙인다. ### NSG 규칙 하위 청크의 본문이 "아웃바운드는 명시 요청 없으면 추가하지 않는다" 한 줄이면, 그 벡터 안에는 어느 프로젝트의 무슨 NSG 인지가 전혀 없다. 조상 헤더와 경로를 붙이면 그 단어들이 벡터에 들어간다.

분할기가 셋이다.

md_splitter     마크다운 헤더(h1~h4) 경계
infra_splitter  \nresource · \nmodule · \ndata · \nvariable · \noutput · \nlocals
size_capper     위로 자른 뒤에도 긴 것을 1200 자로 재단

infra_splitter 가 HCL 을 아는 부분이다. 앞의 구분자부터 시도하고 안 되면 뒤로 물러난다. 그래서 .tf 청크의 80% 가 최상위 블록에서 시작한다.

③ chroma_store.py — 저장소 연결#

CHROMA_URL 환경변수가 있으면 원격 서버, 없으면 로컬 디렉토리를 쓴다. 호출부 셋(build_index, query, api)은 어느 쪽에 붙는지 몰라도 된다.

describe() 는 로그용인데 URL 속 비밀번호를 반드시 가린다.

④ query.py — 질의 + 설정의 정본#

여기가 설정의 단일 출처다. api.py 와 evaluate.py 가 여기서 상수와 함수를 가져다 쓴다. 고칠 일이 있으면 여기만 고치면 된다.

함수 하는 일
priority_groups() SOURCES 를 우선순위별로 묶음
search_by_priority() 레퍼런스별로 따로 검색
control_context() 통제 문서 5 개를 data/ 에서 직접 읽음
build_prompt() 지시문 + 통제 규칙 + 검색 근거 + 질문 조립

주요 상수:

EMBED_MODEL= 환경변수 RAG_EMBED,       기본 bge-m3

⑤ api.py — HTTP#

로직을 새로 쓰지 않고 query.py 의 함수를 그대로 쓴다.

경로 필요한 것 용도
GET /health 없음 Chroma·Ollama 각각 확인
GET /search/text Chroma 만 글자 그대로 찾기. Ollama 없어도 됨
GET /search +임베딩 청크와 거리만. 답 생성 없음

/search 가 거리를 돌려주는 것은 의도적이다. 프롬프트 레이어를 따로 두려는 쪽은 이 값으로 판정하고 자기 프롬프트를 조립하면 된다. 순서를 뒤집어 이 API 아래에 프롬프트를 끼우면 프롬프트가 두 겹이 되어 서로 싸운다.

⑥ evaluate.py — 측정#

eval_questions.json 의 47 문항을 돌려 검색 품질과 라벨 준수를 잰다. 8 절 참고.

5. 답변의 대괄호는 무엇인가#

이 시스템의 핵심 산출물이다. 답변의 각 항목 앞에 근거의 출처를 표시한다.

[Landing Zone 기준]  출처가 lz-reference/ 로 시작하는 내용
[Workload 기준]      출처가 wl-reference/ 로 시작하는 내용
[표준 모듈 기준]      출처가 azure-standard/ 로 시작하는 내용
[AI 제안]            문서에 없어 모델의 일반 지식으로 답한 내용
[추가 확인 필요]      문서가 기준만 주고 확정값은 남겨 둔 것

왜 필요한가#

사용자가 답을 보고 "이게 우리 표준인가, 모델이 아는 일반론인가" 를 구분할 수 있어야 한다. 그 구분이 없으면 RAG 를 쓰는 의미가 없다.

라벨은 어디에 정의돼 있나#

위치 역할
lz-reference/01-scope-and-reference-policy.md 7 절 원본 규정. 표기의 정본
query.py:85~89, :139~141 프롬프트에서 모델에게 지시
evaluate.py:71~86 평가가 라벨을 출처에 묶어 판정

01-scope-and-reference-policy.md 는 통제 문서라 매 질문마다 프롬프트에 통째로 들어간다. 모델이 라벨을 아는 이유가 이것이다.

라벨을 바꾸려면 query.py 와 evaluate.py 를 같이 고쳐야 한다. 한쪽만 고치면 평가가 못 알아본다. 그리고 원본 문서의 표기와 어긋나면 안 된다 — 그 문서가 프롬프트에 같이 들어가서 모델에게 서로 다른 라벨을 동시에 가르치게 된다.

원본과 다른 점#

  • [표준 모듈 기준] 은 우리가 만들었다. 원본은 Azure CLI 생성기라 테라폼 표준 모듈이라는 출처가 없었다. 원본의 [레퍼런스 2 보완] 자리에 해당한다.
  • [레퍼런스 2 보완] 은 안 쓴다. 두 번째 승인 레퍼런스가 아직 없다.

아직 안 쓰는 판정값#

레퍼런스의 15-validation-rules.md 는 REJECT / REVIEW_REQUIRED / AUTO_ADD / DEPENDENCY 도 규정한다. 우리는 안 쓴다. CTRL-001~005 는 설계 산출물을 심사하는 규칙인데 Q&A 조수가 스스로 REJECT 를 선언하면 월권이다. 설계 생성기로 확장하면 그때 필요해진다.

6. 중점적으로 설계한 것#

6.1 실패가 두 종류이고 막는 수단이 다르다#

이게 이 프로젝트에서 제일 중요한 통찰이다. 대부분 첫 번째만 생각한다.

A. 없는 걸 지어냄 B. 비워 둔 값을 채움
예 "AKS 모듈 만들어 줘" "우리 MG 계층 어떻게 잡아?"
검색 실패 — 관련 없는 청크만 성공 — 맞는 문서가 걸림
거리 멀다 (0.93~) 가깝다 (0.70)
왜 틀리나 표준에 없는 걸 지어냄 문서가 일부러 비워 둔 칸을 채움
막는 것 거리 임계값 프롬프트뿐

B 가 진짜 문제다. 레퍼런스는 "조직 규모에 따라 확정한다" 처럼 기준만 주고 값은 의도적으로 비워 둔다. 모델이 도움이 되고 싶어서 구체적인 MG 이름이나 CIDR 을 채우면 틀린 답인데, 거리가 낮아서 어떤 임계값도 못 잡는다. 게다가 근거가 붙어 있어서 검증된 것처럼 보인다.

그래서 프롬프트에 두 절이 들어가 있다.

  • 생성하지 않을 값 — Tenant ID, Subscription ID, CIDR, DNS Zone 이름, ExpressRoute 회선 등 (레퍼런스 6 절 목록 그대로)
  • 기준과 값을 구분한다 — "…에 따라 확정한다" 를 만나면 기준을 제시하고 값은 [추가 확인 필요] 로

그리고 평가에 value_withheld 갈래가 따로 있다.

6.2 레퍼런스별로 따로 검색한다#

스펙(wl-reference/15-rag-metadata-and-chunking.md 4·9 절)이 통합 검색을 금지한다.

모든 레퍼런스를 한꺼번에 유사도 검색한 뒤 점수가 높은 순으로만 정렬하면 우선순위가 깨질 수 있으므로 레퍼런스별로 검색한다. 유사도 점수로 authority 또는 priority 를 재정렬하지 않는다.

점수 높은 Workload 조각이 Landing Zone 필수 기준을 밀어내면 안 되기 때문이다. 거리는 같은 레퍼런스 안에서만 순서를 정한다.

그래서 -k 의 뜻이 "전체 몇 개" 가 아니라 "레퍼런스별 몇 개" 다. 소스가 셋이면 최대 3k 개가 나온다. 기본값 3.

이 설계가 실제로 답을 구한 사례가 있다.

질문      STG 와 DEV 를 분리해야 하나
최단거리  1.039  azure-standard/modules/network/appgw/README.md   ← 무관한 문서
정답문서  lz-reference/03-management-group-subscription.md        ← 더 멀리 있었다
답변      [Landing Zone 기준] Subscription 분리 판단 기준에 따라…  ✓

거리만 보면 실패했을 질문이다. 레퍼런스별로 3 개씩 강제로 뽑는 구조가 lz 청크의 자리를 보장해서 답이 나왔다.

6.3 통제 문서는 검색하지 않고 항상 넣는다#

참조정책·검증규칙·연결계약 5 개는 질문과 무관하게 항상 프롬프트에 들어간다.

lz-reference/01-scope-and-reference-policy.md
lz-reference/15-validation-rules.md
lz-reference/16-workload-integration-contract.md
wl-reference/01-reference-policy.md
wl-reference/11-validation-rules.md

합쳐서 16,572 자다. Source.pinned 로 지정하면 category 가 control 이 되어 build_index 가 인덱싱하지 않고, query.control_context() 가 data/ 에서 직접 읽는다.

인덱스에 두면 두 가지가 나빠진다. 질문과 상관없는 CTRL-003 REJECT 조항이 근거로 딸려 오고, 정작 필요할 때는 유사도가 낮아 빠질 수 있다.

이것 때문에 num_ctx 가 24576 이어야 한다. 기본값 4096 으로는 통제 문서만으로도 넘친다. 잘렸다는 경고가 없어서 답만 조용히 부실해진다.

6.4 잘린 표 조각에 머리글을 되돌린다#

긴 표가 청크 크기에 걸려 잘리면 두 번째 조각부터 머리글 행을 잃는다.

| | 웹로그 수집 서버 #2 | | disk-prd-wcap-02-logs-01 | ... | 64 | ...

64 가 디스크 GB 인지 메모리인지 사람도 임베딩도 모른다. 실측으로 "운영계 WEB 서버 사양" 질문에 답하지 못했고 거리가 0.834 까지 밀렸다(잘 되는 질문은 0.490).

한 번 틀린 방향으로 갔다가 고쳤다. 처음엔 절 안의 첫 표 머리글만 찾아 절 전체에 붙였는데, 표가 여럿이면 뒤쪽 조각에 앞쪽 머리글이 붙어서 뜻을 틀리게 알려 줬다. 거리가 0.843 으로 오히려 밀렸다. 머리글이 없는 것보다 나빴다. 그래서 지금은 표마다 시작 위치를 들고 조각 바로 앞의 것을 고르며, 못 찾으면 안 붙인다.

이건 스펙 요구사항이기도 하다 — "표의 제목과 행을 함께 유지한다"(3 절).

6.5 무엇을 넣지 않을지를 한 곳에 모은다#

RAG 에는 문서 단위 권한이 없다. collect_docs.py 의 SOURCES 가 그 결정을 모아 두는 자리다. 실측으로 확인한 제외 대상 둘:

목차 파일 — 모든 주제를 나열하니 모든 질문에 어중간하게 가깝고 정작 답할 내용은 없다. wl-reference/00-index.md 가 "Azure Spring Apps 배포"(0.785)와 "Azure Functions 앱 배포"(0.786) 양쪽에서 1 위로 걸렸다. 코퍼스에 없는 주제인데도. 이 둘이 정상 질문과의 간격을 0.036 에서 0.014 로 좁혔다.

Azure CLI 생성 문서 — .ps1 산출물을 규정한다. 테라폼 생성기엔 틀린 출력 형식이라 검색되면 모델이 az 명령을 뱉는다.

6.6 거리 임계값은 도입하지 않았다#

원래는 "거리가 임계값을 넘으면 LLM 을 부르지 않고 없다고 답한다" 를 넣으려 했다. 접었다. 간격이 이렇게 움직였기 때문이다.

표본 1 개                0.272
표본 15 개               0.036
레퍼런스 35 장 추가       0.014
목차·CLI 문서 제외        0.036

문서가 늘수록 좁아진다. 구조적인 문제다 — bi-encoder 는 질문과 문서를 각각 독립적으로 벡터화해서 거리만 재기 때문에 "이 문서가 이 질문에 답하는가" 를 판단하지 못한다. 그냥 "주제가 비슷한가" 만 본다.

대신 라벨이 그 역할을 하고 있다. gemma3:12b 실측으로 47 문항 중 46 이 기대한 라벨을 달았다. 그리고 스펙 9 절도 거리로 자르는 것을 금지한다 — "유사도 점수만으로 필수 규칙을 제거하지 않는다."

6.7 측정 도구를 먼저 만들었다#

evaluate.py + eval_questions.json. 코퍼스를 바꿀 때 질문지는 건드리지 않는다. 도구와 대상을 같이 바꾸면 무엇 때문에 숫자가 움직였는지 알 수 없다.

6.8 모델은 gemma3:12b 로 확정했다#

공개 벤치마크로는 이 용도를 가릴 수 없었다. HCL 은 코딩 벤치마크에 거의 없고, "근거를 라벨로 표시하는" 성향은 아예 재지 않는다. 그래서 47 문항으로 직접 쟀다.

gemma3:12b qwen2.5:14b
라벨 준수 46/47 39/47
라벨 없음 0 건 2 건
라벨 이름 오류 없음 Voting Zone, Parking Zone, [문서] 등
47 문항 소요 1,484 초 1,522 초

라벨 이름을 망가뜨리는 게 결정적이었다. qwen 은 Landing Zone 을 "Voting Zone", "Parking Zone" 으로 쓰거나 [문서] 같은 없는 라벨을 만들었다. 라벨이 이 시스템의 산출물인데 표기가 흔들리면 쓸 수 없다.

컨텍스트 예산도 gemma 쪽이다. 통제 문서 때문에 num_ctx 24576 이 필요한데, Gemma 3 는 레이어 6 개 중 5 개가 슬라이딩 윈도우(1024)만 봐서 컨텍스트를 늘려도 KV 캐시가 선형으로 안 는다. qwen2.5:14b 는 가중치 11GB 에 KV 3GB 대라 T4 16GB 에서 빠듯하다.

속도는 갈리지 않았다. 3GB 가벼운데 시간이 같은 것은 gemma 가 답을 더 길게 쓰기 때문이다. 속도를 근거로 삼을 수 없다.

모델을 바꿀 때는 --ask 로 47 문항을 다시 돌려 라벨 준수를 확인할 것.

9. 자주 걸리는 함정#

9.1 Windows 관련#

PYTHONUTF8=1 을 안 넣으면 깨진다. collect_docs.py 가 git 로그를 읽을 때 OS 기본 코드페이지로 디코딩하면 한국어 커밋 메시지가 깨진다. 코드에서 인코딩을 못박아 뒀지만(encoding="utf-8"), 콘솔 출력을 파일로 리다이렉트할 때는 여전히 필요하다.

경로 구분자. Windows 는 \ 라서 ".terraform/" 같은 제외 패턴이 매칭되지 않는다. excluded() 가 비교 전에 / 로 통일한다. 이걸 빼면 terraform init 한 번에 벤더링된 모듈이 조용히 코퍼스에 들어간다.

Ollama 데스크톱 앱은 서비스가 아니라 트레이 앱이다. 띄운 사용자가 로그오프하면 같이 죽는다. RDP 는 로그아웃 말고 연결 끊기로 나올 것. 환경변수도 앱을 완전히 종료(트레이 아이콘 → Quit)했다가 다시 띄워야 반영된다.

Git Bash 에서 set 은 안 통한다. set RAG_LLM=gemma3:12b 는 cmd 문법이다. bash 에서는 export RAG_LLM=gemma3:12b 또는 RAG_LLM=gemma3:12b python ....

9.2 -k 의 의미#

"전체 몇 개" 가 아니라 "레퍼런스별 몇 개" 다. 소스가 셋이라 -k 6 이면 청크 18 개가 들어간다. 통제 문서 16,572 자에 더해지면 컨텍스트를 위협하고 느려진다. 기본값 3 을 그대로 쓰면 된다.

9.3 pull 만 하고 재인덱싱을 안 함#

코드를 받아도 chroma_db/ 는 안 바뀐다. 청킹이나 제외 규칙을 고친 커밋을 받았으면 반드시 collect_docs.py → build_index.py --full 을 다시 돌린다.

증상: 제외했어야 할 파일이 검색 결과에 계속 나온다.

9.4 uv.lock 충돌로 pull 이 막힘#

uv sync 가 VM 환경에 맞게 lock 을 다시 쓴다. 그러면 git pull 이 Your local changes ... would be overwritten 으로 중단된다.

git checkout -- uv.lock
git pull origin main

lock 은 원본에서 언제든 다시 만들 수 있으니 버려도 된다.

9.5 venv 활성화를 깜빡함#

source .venv/Scripts/activate

안 하면 시스템 파이썬이 돌아 ModuleNotFoundError: langchain_chroma 가 난다. 셸 창마다 다시 해야 한다.

uv run python ... 을 쓰면 활성화 없이도 되지만, 활성화돼 있으면 그냥 python 으로 충분하다.

9.6 첫 답이 느림#

질문당 30 초 안팎이 정상이다. 통제 문서 16,572 자를 매번 프롬프트 처리해야 한다. ollama ps 에서 100% GPU 인지 확인할 것. 45%/55% CPU/GPU 같은 게 보이면 VRAM 이 모자라 CPU 로 넘친 것이고, 그러면 vCPU 4 개로 계산하느라 체감이 무너진다.

10. 아직 안 정한 것 / 남은 일#

모델은 gemma3:12b 로 확정했다. 기본값이 그것이라 RAG_LLM 을 따로 줄 필요가 없다. 고른 근거는 6.8 절에 있다.

10.1 라벨 정확도 검사가 느슨하다#

지금 검사는 "맞는 라벨이 답변 어딘가에 있나" 만 본다. 답변을 여러 항목으로 쪼개 쓰면서 첫 항목에 틀린 라벨을 붙여도 뒤에 맞는 게 나오면 통과한다.

실제로 두 건이 이렇게 통과했다.

이름이 예약된 서브넷            근거 azure-standard/... 인데 [Landing Zone 기준]
스토리지 계정 서비스 엔드포인트  근거 azure-standard/... 인데 [Landing Zone 기준]

"틀린 라벨이 없는가" 를 추가로 봐야 한다. evaluate.py 에 조건 한 줄이면 된다.

10.2 스펙과 아직 다른 부분#

wl-reference/15-rag-metadata-and-chunking.md 2 절이 요구하는 메타데이터 중 reference_id · owner · evidence_type · environment · workload_type · version 은 아직 안 넣었다. authority 와 priority 만 넣었다.

7 절의 검색 결과 포맷([SOURCE] 블록에 메타데이터, [CONTENT] 에 본문)도 아직 안 맞췄다. 지금은 breadcrumb 한 줄이다.

10.3 범위 자체가 더 크다#

레퍼런스의 시스템 프롬프트 템플릿(wl-reference/14-system-prompt-template.md)을 보면 최종 목표는 Q&A 도구가 아니라 설계 생성기다.

스펙 지금
입력 자연어 요구사항 질문
출력 11 단계 구조 + 코드 답변
검증 Python Rule Engine 없음
판정 REJECT / REVIEW_REQUIRED / AUTO_ADD / DEPENDENCY 라벨 5 개

특히 이 줄이 중요하다.

Prompt 만으로 필수 규칙 준수를 보장하지 않고 Python Rule Engine 으로 결과를 다시 검증한다.

지금 만든 것은 그 시스템의 검색 계층에 해당한다.

10.4 앞으로 들어올 것#

AKS · PostgreSQL · Redis 등 자주 쓰는 모듈이 azure-terraform-standard 에 추가될 예정이다. 들어오면:

  1. python collect_docs.py && python build_index.py --full
  2. python evaluate.py --save 새이름 --compare 기준이름
  3. 평가가 "들어온 것 같다" 로 알려 주는 항목을 eval_questions.json 에서 planned → present 로 옮기고 expect 를 달아 준다

질문지를 안 옮기면 평가가 정상 동작을 "지어냈다" 고 잘못 보고한다.

11. 한 문단 요약#

사내 Azure 표준 문서를 벡터 검색 가능한 형태로 인덱싱해서, 질문이 오면 관련 문서를 찾아 LLM 에게 근거로 넘기는 시스템이다. 목표는 코드 생성이 아니라 근거의 출처를 분명히 하는 것이다. 표준에 없는 걸 물으면 [AI 제안] 으로 표시하고, 표준이 판단 기준만 주고 값을 비워 둔 항목은 [추가 확인 필요] 로 남긴다. 후자가 더 어려운데 검색은 성공하지만 모델이 빈칸을 채워 버리기 때문이다. 거리로는 못 잡아서 프롬프트로 막는다. 고정 질문지 47 개로 이 동작을 계량화하고 있고, 현재 gemma3:12b 기준 46/47 이다.
